# 容器化部署与模块边界

## 一、设计目标

本项目要求各模块保持解耦，能够按阶段合并部署，也能够在需要时单独容器化。

设计原则：

```text
每个模块职责单一
模块之间通过 HTTP / 消息队列 / 配置通信
数据库和召回策略不直接绑定
服务可以独立启动、独立替换、独立扩展
```

## 二、推荐容器列表

### 1. agent-service

职责：

```text
LangChain / LangGraph Agent 编排
用户意图识别
工具调用
调用 rag-gateway
生成最终回答
```

不负责：

```text
向量检索
数据库底层查询
文档入库
```

### 2. rag-gateway

职责：

```text
统一 /retrieve 入口
检索计划生成
策略选择
结果聚合
知识包返回
```

### 3. retriever-runtime

职责：

```text
执行召回策略
调用索引适配器
结果融合、去重、排序
父文档扩展
图片证据附加
```

### 4. adapter-postgres

职责：

```text
PostgreSQL / pgvector 查询
元数据过滤
Chunk 取回
父文档扩展
图片 URL 查询
检索日志写入
```

### 5. adapter-opensearch

职责：

```text
关键词检索
BM25 检索
过滤检索
```

### 6. adapter-vector

职责：

```text
Qdrant / Milvus 向量检索
多集合向量查询
向量索引管理
```

第一阶段如果只用 pgvector，可以暂不启用。

### 7. adapter-graph

职责：

```text
实体检索
图谱扩展
路径查询
GraphRAG
```

第一阶段可预留。

### 8. ingestion-service

职责：

```text
文件解析
语义切分
摘要生成
预设问题生成
OCR
EmbeddingTask 生成
IndexTask 生成
```

### 9. metadata-service

职责：

```text
文档元数据
Chunk 元数据
数据资产元数据
版本状态
权限信息
```

第一阶段可合并在 PostgreSQL + rag-service 中。

### 10. object-service

职责：

```text
PDF、图片、附件存储
生成访问 URL
对象权限
```

可使用 MinIO。

### 11. postgres

职责：

```text
结构化元数据
pgvector 向量
检索日志
数据资产
```

### 12. redis

职责：

```text
缓存 query embedding
缓存热门检索结果
会话状态
异步任务状态
```

## 三、阶段化部署

### 阶段 1：最小部署

```text
agent-service
rag-service
postgres
```

其中 `rag-service` 合并：

```text
rag-gateway
retriever-runtime
adapter-postgres
部分 ingestion 能力
```

适合快速演示。

### 阶段 2：入库与检索分离

```text
agent-service
rag-gateway
ingestion-service
postgres
minio
```

### 阶段 3：召回执行拆分

```text
agent-service
rag-gateway
retriever-runtime
adapter-postgres
ingestion-service
postgres
minio
redis
```

### 阶段 4：多数据库后端

```text
agent-service
rag-gateway
retriever-runtime
adapter-postgres
adapter-opensearch
adapter-vector
adapter-graph
ingestion-service
postgres
opensearch
qdrant
neo4j
minio
redis
```

## 四、服务通信

推荐优先使用 HTTP，后续引入消息队列。

```text
Agent → RAG Gateway：HTTP
RAG Gateway → Retriever Runtime：HTTP
Retriever Runtime → Adapter：HTTP 或内部 SDK
Ingestion → Adapter：HTTP / 消息队列
Adapter → Database：数据库协议
```

异步任务可使用：

```text
Redis Queue
Celery
RabbitMQ
Kafka
```

第一阶段无需上复杂消息队列。

## 五、配置中心

所有组合关系通过配置声明，不写死在代码中。

```yaml
backends:
  postgres_pgvector:
    service_url: http://adapter-postgres:8000
    capabilities:
      - vector_search
      - metadata_filter
      - chunk_fetch
      - parent_expand
      - asset_fetch
      - data_asset_search

  opensearch_main:
    service_url: http://adapter-opensearch:8000
    capabilities:
      - bm25_search
      - keyword_search

strategies:
  hybrid:
    required_capabilities:
      - vector_search
      - bm25_search

  image_context:
    required_capabilities:
      - vector_search
      - asset_fetch
```

## 八、健康检查

每个容器应提供：

```text
GET /health
GET /capabilities
```

`/capabilities` 返回：

```json
{
  "service": "adapter-postgres",
  "capabilities": [
    "vector_search",
    "chunk_fetch",
    "asset_fetch"
  ],
  "status": "ok"
}
```

每次检索需要记录：

```text

```

用于：

```text
调试

```

## 十、总结

容器化设计的重点不是一开始就拆很多服务，而是保证边界清楚。

第一阶段可以合并部署，但代码和接口要按照以下边界组织：

```text
Agent 编排
RAG 编排
召回策略执行
数据库适配
数据入库
对象存储
```

这样后续无论是接入 pgvector、OpenSearch、Qdrant、Neo4j，还是增加新的召回策略，都不需要推翻整体结构。
