> 现状请看：`README.md`、`docs/00_项目结构.md`、`docs/09`、`docs/11`、`docs/10`。

**Review 日期**: 2026-07-06
**Review 视角**: 以真实用户从"新建项目 → 导入文本 → 切分 → 转脚本 → 实体绑定 → 提示词 → 生成视频"的完整操作路径为主线，评审数据 CRUD 的完整性、服务配置的实际调用链路、LLM 的实际使用方式。
**总体结论**: 相比上一轮（docs/04），P0 断链和大部分 P1 已修复，前端结构性问题（F-1/F-2/F-5/F-6）也已落地。但从用户操作视角看，仍存在 **三条主线级断裂**：① 素材上传后从未进入视频生成请求（实体一致性链路仍是断的）；② 全系统没有任何真实 LLM 调用，LLM 配置是"死配置"；③ 视频生成引擎永远使用 Mock 适配器，视频 API 配置同样是"死配置"。另有多处删除能力缺失、确认门可被绕过、以及破坏性操作确认时机错误的问题。

## A. 主线级链路断裂（最优先）

### A-1 实体卡素材从未进入视频生成请求 —— 素材绑定是"死功能"

用户完整走完操作流：上传参考图/音频/视频 → 创建实体卡 → 智能绑定 → 确认 → 生成视频。但：

- `App.jsx` 的 `generatePreview` / `generateFull`（621-629、661-669 行）构造请求时**根本不带 `assets` 字段**；
- `GenerateVideoRequest.assets` 默认空 dict，后端照单全收；
- `retry` 复制的也是空 assets。

结果：`VideoTask.assets` 永远为 `{}`，用户精心维护的实体卡素材（canvas 的核心差异化能力"实体一致性"）对生成结果**零影响**。这是 docs/05 F-4 的残留，也是当前最严重的产品级问题。

**修复**：生成前收集当前片段已确认绑定的实体 → 取其卡片的 `reference_images/audio_samples/video_clips` → 组装进 `assets`；后端 `_ensure_video_generation_allowed` 应校验"绑定的实体卡引用的素材文件存在"。

### A-2 视频生成引擎永远是 Mock —— 视频 API 配置是"死配置"

`api/app.py:75`：

```python
video_engine = VideoGenerationEngine(archive_root=...)   # api_client 参数未传 → 永远 MockVideoAPIAdapter
```

用户在设置页填了 videoProvider/videoBaseUrl/videoApiKey、预检显示"通过"，然后点"完整生成"——实际走的是 Mock：瞬间完成，产物是一个 `.txt` 文本文件（`MockVideoAPIAdapter.download_result` 写文本；`_archive_path` 后缀写死 `.txt`）。**付费配置从头到尾没有任何消费方**，且 UI 不给出任何"当前是 Mock/离线模式"的提示，用户会误以为真的生成了视频。

**修复**：`create_app` 里根据 `_load_api_config` 的 `videoProvider` 构造真实适配器（`offlineMode=True` 或 provider=mock 时才用 Mock）；配置变更后重建/热切换引擎；所有任务结果标注 `provider: mock|real`，前端在生成按钮旁常驻显示当前 provider。

### A-3 全系统没有任何 LLM 调用 —— LLM 配置同样是"死配置"

`llmProvider/llmBaseUrl/llmApiKey` 被保存、加密、解密、预检展示，但**代码里没有一个调用点**（详见 D 节）。脚本转换、实体提取、切分建议全部是规则/正则实现。docs/04 P1-3/P1-4 规划的 `LLMClient` 协议 + `MockLLMClient` 降级结构没有实现。当前产品名义上是"AI 视频创作管理"，文本处理链路里实际没有 AI。

## B. 数据增删改查（CRUD）评审

按数据对象逐一过：

### B-1 文档：导入端点前端不可用 + 服务器路径安全隐患

- `/api/documents/ingest` 要求传**后端服务器文件系统路径**（`IngestDocumentRequest.path`），浏览器用户根本无法提供；前端也确实**从未调用**该端点——唯一的文本入口是预处理页的 textarea 手工粘贴。canvas 要求的"txt/docx 文件导入"对 UI 用户不存在。
- 该端点还接受任意绝对路径（无目录白名单校验），等于开放了"读服务器任意 .txt/.md/.docx"的能力（本地部署风险低，但属于不该有的口子）。

**修复**：新增 `POST /api/documents/upload`（multipart 或 base64，与素材上传同构），文件落到 `projects/{id}/inputs/`，解析出文本写入 workspace 的 `documentText`；`ingest` 保留给 CLI 但限制在 workspace 根目录内。

### B-2 文档/片段/脚本：两条互不相通的持久化路径

- `/api/documents/split` 每次新建一个丢弃型 `Project(name="inline")`，Document/Segment **不落库**，只把结果返回给前端塞进 workspace JSON；
- `/api/documents/ingest` 会 `save_document`，但 split 路径完全不用它；
- `storage.save_scripts` 是 no-op（storage.py:284-287），documents/segments 表形同虚设。

直接后果：**每次重新切分，segment id 全部重新生成**，而 `video_tasks` 表按旧 segment_id 记录历史 → 重切分后 VideoView 的任务分组出现一堆"孤儿片段"（`segment-unknown`），版本号 v1/v2 的连续性也断了。"归档 + 版本对比"在一次重切分后就不可用。

**修复**：切分落库（document + segments 归属真实 project），或至少在重切分时对旧 video_tasks 做迁移标记（`orphaned: true`）并在 UI 单独分组为"历史版本（结构已变更）"。

### B-3 实体卡：后端有改/删 API，前端没有任何入口

`PUT/DELETE /api/projects/{id}/entity-cards/{card_id}` 都实现了，但 `ResourceView` 的卡片列表是纯展示：名字打错、素材传错、状态要改——用户唯一的办法是再建一张新卡，旧卡永远留着。canvas 的"组合生成新状态卡""场景模板包导入"也没有入口。

**修复**：卡片列表增加 编辑/删除/复制为新状态 三个操作；删除时确认框列出"有 N 个实体当前绑定到此卡"。

### B-4 素材文件：只有 Create，没有 Read/Delete，且中文文件名被销毁

- `_safe_filename`（storage.py:204-206）把非 ASCII 全替换为 `_`：`小明参考图.png` → `_.png`、`小红参考图.png` → `_.png` → 靠 `_2` 后缀去重。用户上传 10 张中文命名图片后，assets 目录是 `_.png, _2.png, ..., _10.png`，与卡片的对应关系完全靠猜。
- 没有素材列表/预览端点：卡片里存的是相对路径字符串，前端展示的只是"图 2 / 音 1 / 视 0"的计数，用户**无法查看自己传的是哪张图**，更无法删除传错的文件。
- 删除实体卡不清理素材文件 → 孤儿文件持续累积，没有任何清理机制。
- 25MB 的 base64 上传限制对视频素材明显不够，且 base64+JSON 方式内存放大 ~33%。

**修复**：文件名保留 Unicode（只过滤路径分隔符和控制字符）；增加 `GET /api/projects/{id}/assets`（列表）+ 静态文件挂载（预览）+ `DELETE`（带引用计数检查）；视频类素材改 multipart 流式上传。

### B-5 项目：不能删除、不能归档

`POST/GET/PUT /api/projects` 齐了，但没有 DELETE，也没有"归档"状态。测试建的废项目会永远留在列表里。category 只有前端硬编码的过滤用途。**修复**：软删除（`archived_at` 字段）+ 列表默认过滤 + 回收站视图。

### B-6 视频任务：不能删除、不能取消，重试无成本确认

- 任务只增不减，失败任务、Mock 试验任务全部永久堆积；
- 任务是同步执行的（见 C-5），无法取消；
- **"重试"按钮对完整生成任务同样一键直发**（`retryVideoTask` 无确认弹窗），而"完整生成"按钮有二次确认——同一个付费动作两个入口一个有闸门一个没有，重试等于绕过成本闸门。

**修复**：重试非预览任务复用 `askConfirm` 成本确认；增加任务删除（仅 failed/completed）；长任务改异步后支持取消。

### B-7 破坏性确认的时机放错了位置

`splitDocument`（App.jsx:284-322）在**获取切分建议之前**弹"将清空脚本/实体/提示词"的危险确认——但这一步只是查看建议，什么都不清。真正清空数据的是 `applySplitSuggestion`（334-342 行），它**没有任何确认**。用户完全可能：昨天点过"切分建议"，今天回来直接点"应用方案"，下游数据无提示全灭。docs/05 规划的"重切分前自动保存检查点"也没有做。

**修复**：确认框移到 `applySplitSuggestion`；应用前自动 `save_checkpoint`；查看建议不需要确认。

### B-8 重新提取实体会静默清空所有人工确认

`extractEntities` 直接 `entities: data.entities.map(e => ({...e, confirmed: false}))` 全量覆盖。用户确认了 20 个实体后想"再提取一次看看有没有漏的"→ 所有确认状态清零，且无确认弹窗。**修复**：按 (name, type) 合并保留已确认项，或至少弹确认框。

### B-9 脚本"人工确认"没有任何下游消费方

预处理页有"人工确认"按钮和 confirmed 状态，但 `_sync_project_flags_from_workspace` 里 `has_scripts` 只看脚本非空（storage.py:596），未确认/校验不合格的脚本照样能进提示词和生成环节。质检环路（转换合格判断）是纯装饰。**修复**：`has_scripts` 至少要求全部片段 `status in (converted, confirmed)`；或增加独立 flag `scripts_confirmed` 进入 ENTITIES_EXTRACTED 前置条件。

### B-10 实体提取把所有脚本拼成一个字符串，丢失片段归属

`extractEntities` 用 `Object.values(workspace.scripts).join('\n\n')` 全量提取，实体表是全局的，无法知道"小明出现在哪几个片段"。到生成环节（按片段生成）时，无法按片段挑选相关实体的素材——这也是 A-1 难以正确修复的结构性原因。**修复**：按片段提取并在实体上记录 `segment_ids: []`。

### B-11 检查点：前端从未使用，恢复也只恢复标志位

- `GET /api/checkpoints/{project_id}` 和 `POST /api/checkpoints/load` 前端零调用，UI 上没有任何检查点入口；
- `restore_checkpoint`（storage.py:433+）只恢复 project 的 current_state 和 has_* 标志，**不恢复 workspace 内容**——用户期望的"回溯到请求前状态"（文本、脚本、提示词回到当时的样子）实际不会发生，回溯后界面数据不变、只有步骤条变了，属于会误导用户的半实现。
- 检查点也只在 `workflow.jump_to` 命中 3 个状态时创建，而前端从不调用 `/api/workflow/jump`（步骤条只是切视图），所以**实际运行中一个检查点都不会产生**。

**修复**：检查点 data 应包含 workspace 快照；恢复时同时写回 workspace；在破坏性操作（应用切分、重提实体）前由 API 自动创建检查点；VideoView 增加检查点列表 + 恢复入口。

### B-12 工作区全量 PUT + 每次保存重算状态，覆盖显式流程操作

`save_workspace` 每次都 `_sync_project_flags_from_workspace` + `_derive_current_state` 重算并回写 current_state。这意味着：

- `/api/workflow/jump` 显式跳转的状态，会被下一次 350ms 防抖的自动保存**静默改回推导值**——jump 端点等于没用（前端也确实没用它，两者互为因果）;
- 多标签页/前后端并发时 last-writer-wins，无版本号/ETag 检测，旧快照会整包覆盖新数据。

**修复**：workspace 增加 `revision` 字段做乐观锁（PUT 带 revision，不匹配返回 409）；`current_state` 的推导只在"推导值高于当前值"时前进，或干脆区分 `derived_state` 与 `pinned_state`。

## C. 服务配置功能调用评审

### C-1 autoApprove 闸门是客户端说了算，服务端未强制

绑定确认的自动同意逻辑在 `/api/projects/{id}/entities/smart-bind` 里由**请求体参数** `auto_approve` / `auto_approve_threshold` 控制，服务端不读自己存的 `api_config.autoApprove`。前端传的是 boot 时缓存的旧配置（`apiConfig.autoApprove`），设置页改完开关后，资源页用的还是旧值（除非刷新）。更重要的是：docs/04 P1-7 明确要求"确认闸门服务端强制"，现在闸门参数完全由客户端提供。**修复**：服务端读取自己的配置作为准绳，请求参数只允许"比配置更严格"。

### C-2 assets_confirmed 被自动推导，人工素材确认门被架空

storage.py:600：

```python
project.assets_confirmed = bool(data.get("assetsConfirmed")) or project.has_bindings
```

只要全部实体点了确认（has_bindings=True），`assets_confirmed` 自动为 True——**与 autoApprove 开关无关**。"素材确认"作为付费生成前的独立人工闸门（canvas 九步流程中的独立一步）实际不存在：没有任何 UI 让用户"确认素材"，它是被 `or` 出来的。`VIDEO_GENERATING` 的前置 `assets_confirmed` 因此形同虚设。**修复**：去掉 `or project.has_bindings`；VideoView 生成输入区展示"将使用的素材清单 + 确认按钮"，确认后才写 `assetsConfirmed: true`（autoApprove=True 时可自动，但要显示"已自动确认"标记）。

### C-3 offlineMode 只影响预检文案，不影响任何行为

`offlineMode` 默认 True，唯一消费方是 `_build_precheck` 的显示逻辑（离线时 LLM/视频检查直接 pass）。它不切换 Mock/真实适配器（引擎反正永远是 Mock，见 A-2），不禁用任何按钮。用户关掉"离线优先"后系统行为没有任何变化。**修复**：offlineMode 成为 A-2 修复中选择适配器的开关，并在前端顶栏显示当前模式徽章。

### C-4 预检是"表单检查"而非"连通性检查"，通过≠可用

预检只检查"字段填没填、模板数>0、磁盘>512MB"，从不请求 llmBaseUrl/videoBaseUrl 验证 key 是否有效。用户填一个错误的 key，预检全绿，直到（未来接真实 API 后）付费调用才失败。**修复**：LLM/视频检查加真实 ping（带超时和"跳过在线检查"选项）；预检结果注明检查方式（`静态检查` vs `已连通`）。

### C-5 密钥损坏被静默吞掉 + 无法主动清除密钥

- `_load_api_config`（config.py:22-25）在 `reveal_secret` 完整性校验失败时 `config[key] = ""` 静默清空——`local_secret.key` 被删/换机器迁移后，用户的密钥无声消失，预检只会显示"需要 API Key"，没有任何"密钥已失效，请重新录入"的提示。
- PUT 语义是"空值=保留原值"（app.py:89-91），因此**没有任何办法删除已保存的密钥**。
- 附带一个前端 bug：`saveApiConfig` 在两个 `await` 之后调用 `event.currentTarget.reset()`（App.jsx:723），React 事件在异步边界后 `currentTarget` 为 null，会抛 TypeError 被 `run()` 捕获——**每次保存配置都会弹一个错误 toast，尽管保存实际成功了**。应在 handler 开头缓存 `const formElement = event.currentTarget`（createTemplate/createEntityCard 已经是这么做的，唯独这里漏了）。

**修复**：reveal 失败返回明确的 `keyCorrupted: true` 状态给前端展示；增加显式"清除密钥"按钮（PUT 传 `null` 表示删除、`""` 表示保留）；修 currentTarget bug。

### C-6 SaveApiConfigRequest 是无校验的自由 dict

`data: dict[str, object]` 任何键值都会被原样存进 settings（provider 拼错、类型错误、注入无关大对象都不报错）。**修复**：定义显式字段的 Pydantic 模型 + provider 枚举校验。

## D. LLM 使用方式评审

### D-1 没有 LLM 客户端抽象，配置无消费方（同 A-3，根因）

规划中的调用链 `convert_to_script → PromptEngine(SCRIPT_CONVERT 模板) → LLMClient` 一环都不存在：

| 环节 | 设计（docs/04） | 现状 |
|------|----------------|------|
| 脚本转换 | LLM + SCRIPT_CONVERT 模板，Mock 降级 | 规则拼接：首行当【场景】，其余整段塞【对白】旁白（document_processor.py:166-176） |
| 实体提取 | LLM + JSON 输出 + 正则兜底 | 纯正则：13 个道具白名单、7 个动词后缀识别人名 |
| 切分建议 | 可后续接 LLM | 三种规则策略并列展示（可接受） |
| 风格推荐 | — | `recommend_style` 关键词匹配，且**没有 API 端点、前端不可见** |

**修复路径**：定义 `LLMClient` Protocol（`complete(prompt, *, json_schema=None, timeout, max_retries)`）+ `MockLLMClient` / `OpenAICompatClient`（读 llmBaseUrl/llmApiKey）；`create_app` 按配置注入；离线/无 key 时自动落到 Mock 并在响应中标注 `engine: "rule"`，前端展示"规则引擎（离线）"徽章，让用户知道自己此刻用的不是 LLM。

### D-2 转换质检环路在逻辑上不可达

`validate_script` 只检查【场景】【动作】【对白】三个标记是否存在，而规则转换器**永远输出这三个标记** → 校验永远通过 → 前端的 `invalid` 状态、"不合格重转"分支是死代码。只有接入真实 LLM（输出不稳定）后该环路才有意义，届时校验也应升级：段落非空、对白格式、长度上下限、（可选）LLM 自评分。

### D-3 提示词渲染只会注入 script 一个变量

`renderPrompt`（App.jsx:579-581）固定 `context: { script: activeScript }`。用户若创建含 `$style`、`$duration` 等变量的模板（模板表单允许），渲染时后端直接 400 "Missing template variables"，且前端没有变量填写表单（docs/05 的 3.5-2 未实现）。**修复**：选择模板后按 `template.variables` 动态生成输入表单，`script` 自动注入，其余用户填写。

### D-4 script_convert / entity_extract 两类模板有名无实

模板分类里 `script_convert` 和 `entity_extract` 可以创建（PromptsView 表单里就有选项），但没有任何代码消费这两类模板——转换和提取都不走 PromptEngine。用户建了这类模板后既不能在任何界面使用，也没有说明。在 D-1 修复前，建议前端先隐藏这两个选项，或标注"预留，接入 LLM 后生效"。

### D-5 未来接入真实 LLM 的两个结构性预备问题

1. **同步阻塞**：当前 API 路由几乎全是 `def`（非 async），Mock 下无所谓；接入真实 LLM/视频 API 后，`convert`（可能 10s+）与 `generate`（分钟级）会占死 worker。转换类应改 async + 客户端受控并发（docs/05 规划的"同时 2 个"目前也没做——`convertAllSegments` 是纯串行 for 循环，且只在**全部完成后**一次性写 workspace，中途关页面全部丢失、期间片段状态徽章不更新）。
2. **无成本/用量记录**：VideoTask 没有 tokens/费用字段，任务列表无法回答"这个月花了多少"。付费产品最少要记 `provider、duration、request_at/completed_at`，费用可后补。
